# AI 生成脚本与答疑演示

适用版本：RowFlow 演示规范 1.0。本文提供可复制的应用提示词、演示需求和验收标准。提示词用于后续 AI 应用，不是新增的 DSL 规范。

## 1. 知识材料怎么分组

| 用途 | 基础材料 | 按需补充 |
| --- | --- | --- |
| 生成完整脚本 | README、01 脚本入口 | 按操作查 02～06；业务契约查 10；完整写法查 11 |
| 平台概念答疑 | 07 架构、08 接入、09 FAQ | 精确语义查 01～06；示例数据查 10 |
| 验收演示 | 本文 | 根据具体案例引用 10、11 及对应规范 |

做知识检索时按二级/三级标题拆分，每个片段保留标题、文件名与适用版本。参数表和紧邻的约束说明一起保存；完整脚本与它的预期结果一起保存。不要只检索 FAQ 而丢失规范来源。

## 2. 代码生成提示词模板

```text
你负责根据提供的 RowFlow 演示规范 1.0 生成业务脚本。

先读取脚本入口规范；按需求检索数据源、Row、操作符、聚合和错误规则。
方法签名与默认值以语法手册为准，请求字段与响应路径以服务契约为准。

交付要求：
1. 输出一个建议的 snake_case.groovy 文件名和完整脚本。需要导入 HTML 演示时同时遵守 15 的注释与解释器约定。
2. 恰好一个 pipeline，指定 dslVersion: '1.0'，声明用到的所有源，恰好一次 emit。
3. 每个闭包显式声明参数，字段统一用 r['field'] 读取。
4. map 返回完整新行；需要保留字段时用 withFields；正确处理空值和数值字符串。
5. 明确关联类型、未命中行为和错误行为。默认使用 fail，只有需求明确允许时才配置降级。
6. 使用文档已有 API。需求超出当前规范时，指出具体能力边界，不静默忽略需求。
7. 缺失 URL、响应路径、RPC 方法契约等关键条件时，说明缺失项并提出精简问题；
   如用户明确要求演示，可改用自包含 memory 数据，并说明这是演示替代。
8. 不猜测真实凭据或服务配置；可以按要求使用文档中的演示占位契约。
9. 脚本后简述输入参数、关键假设、预期结果以及依据的文档章节。
10. 没有实际 RowFlow 宿主的执行证据时，不声称已经运行通过。

用户需求：
{{业务需求}}

可用文档或检索片段：
{{知识材料}}
```

## 4. 脚本生成演示需求

### G01：只依赖内存的入门演示

可复制需求：

> 生成 memory_paid_orders.groovy。用三条内存订单：O1001 已支付 120.50 元、O1002 待支付 80 元、O1003 已支付 200 元。status 使用 PAID/CREATED，amount 为字符串。筛选已支付且金额不低于参数 minAmount 的订单，参数默认 100，按金额降序，只输出 orderId 和数值 amount。使用 RowFlow 1.0。

验收：默认输出 O1003、O1001；金额为数值。写出所有 source、处理链和 emit，无需 HTTP/RPC 配置。参考 [E01](11-完整脚本示例.md)。

### G02：单 HTTP 源

> 使用示例服务契约中的 HTTP 订单接口，生成 http_paid_orders.groovy。tenantId 默认 T001，minAmount 默认 100。筛选 PAID 且金额不低于阈值的订单，按金额降序输出 orderId、userId、数值 amount。读取失败时让任务失败。

验收：按 O1003、O1001、O1005 顺序输出 3 条；配置 rowsPath 为 data.items；不把 minAmount/status 发送成接口未知参数。参考 [E02](11-完整脚本示例.md)。

### G03：多源关联与统计

> 使用示例契约中的 HTTP 订单和 RPC 用户列表，生成 city_sales.groovy。仅统计 PAID 订单；没有用户资料的订单归入“未知”。按城市统计 orderCount、totalAmount、averageAmount，按 totalAmount 降序。任何扫描接口调用失败都使任务失败。

验收：left join；杭州 3 条/370.50 元/平均 123.50，未知 1 条/100 元/平均 100；不得按 userId 去重订单。参考 [E03](11-完整脚本示例.md)。

### G04：按行 RPC 查询与降级

> 使用 O1001/U001、O1003/U001、O1004/U003、O1005/U999 四条内存订单，调用示例 RPC getUser 补充城市，生成 order_user_lookup.groovy。每条订单都保留，未查到、单次源超时或调用失败时城市写“未知”；响应结构、平台权限和任务整体超时仍使任务失败。不要重试。

验收：lookup 源用 recordPath；request 仅提供动态 userId，静态 args 保留 tenantId；`mode: 'left'`、`onError: 'null'`、`retries: 0`。正常响应时 4 次调用、1 行未命中、0 行错误降级。参考 [E04](11-完整脚本示例.md)。

### G05：展开与合并

> 按完整示例 E05 的内存数据，合并 webOrders 和 storeOrders，展开 items，按 sku 统计 itemLineCount 与 totalQty，按 sku 升序，生成 sku_quantities.groovy。

验收：A 的明细行数为 2、数量为 3；B 的明细行数为 1、数量为 1。使用 union + flatMap，空 items 产生零行。参考 [E05](11-完整脚本示例.md)。

## 5. 知识答疑验收集

| 编号 | 用户问题 | 合格回答必须包含 | 主要依据 |
| --- | --- | --- | --- |
| Q01 | Row 为什么底层是 Map，能直接改字段吗？ | Row 是只读记录包装；修改用 map/withFields，嵌套也只读 | [03](03-语法手册-Row与表达式.md) |
| Q02 | map 和 withFields 有什么差别？ | 完整替换与顶层覆盖合并的区别，说明 map 会丢未列字段 | [04](04-语法手册-单流操作符.md) |
| Q03 | rowsPath 和 recordPath 怎样选？ | scan 数组/from，lookup 单对象或 null/lookup；路径缺失是错误 | [02](02-语法手册-数据源配置.md) |
| Q04 | userId 都为空能关联吗？ | join 不匹配；联合键任一分量为空也不匹配 | [03](03-语法手册-Row与表达式.md) |
| Q05 | 为什么一个订单关联后有三行？ | 右表同键三条，一对多展开；核对唯一性和租户维度 | [05](05-语法手册-多源组合与聚合.md) |
| Q06 | lookup 超时可以继续吗？ | 仅显式 onError null 可对源错误降级；平台权限/结构/整体超时不降级 | [06](06-语法手册-执行限制与错误处理.md) |
| Q07 | retries 为 1 最多请求几次？ | 两次，且受幂等、重试类别、任务时限和 lookup 额度约束 | [06](06-语法手册-执行限制与错误处理.md) |
| Q08 | limit(10) 为什么还读取整个右表？ | join 预先构建右表索引，limit 不撤销已发生读取 | [05](05-语法手册-多源组合与聚合.md)、[06](06-语法手册-执行限制与错误处理.md) |
| Q09 | sum 能直接处理字符串金额吗？ | 不能；decimal；null 要先判断 | [03](03-语法手册-Row与表达式.md)、[05](05-语法手册-多源组合与聚合.md) |
| Q10 | 空输入 aggregate 返回什么？ | 全局一行，count/sum 0、其他数值指标 null；分组零行 | [05](05-语法手册-多源组合与聚合.md) |
| Q11 | 重复用户 lookup 能自动复用吗？ | 没有缓存/自动去重；不能为省调用丢掉合法订单 | [08](08-平台知识-接入权限与性能.md) |
| Q12 | 只有结果少于 1000 就不会超限吗？ | 每节点 maxRows、响应大小、lookup 次数和总时限也有约束 | [06](06-语法手册-执行限制与错误处理.md) |
| Q13 | 如何安装 RowFlow，控制台在哪里？ | 资料未提供实现、安装命令或真实控制台，不能编造 | [07](07-平台知识-架构与运行流程.md) |
| Q14 | 示例城市统计为什么是 470.50 元？ | PAID 共四条，杭州 370.50，未知 100，不包括 CREATED 的 80 | [10](10-示例数据与服务契约.md) |

## 6. 能力边界与错误识别测试

这些是用于测试 AI 是否会补出不存在能力的需求或反例，不是推荐写法。

| 编号 | 测试输入 | 预期反应 |
| --- | --- | --- |
| B01 | “给 lookup 开 100 并发，加 30 秒缓存” | 说明 1.0 未定义，不能生成 maxConcurrency/cacheTtl 等键 |
| B02 | “自动遍历 HTTP 的 100 页” | 说明 scan 不自动分页；需要上游聚合接口或先扩展规范 |
| B03 | “把每行发邮件，再 emit” | 说明写入型接口/自行网络调用不在规范内，不能伪造发送方法 |
| B04 | map 闭包返回 null 以过滤 | 指出 RF-TYPE-001，改用 filter 或 flatMap 返回 [] |
| B05 | lookup 源配置 rowsPath | 指出 mode 与路径字段不匹配，RF-CONFIG-001 |
| B06 | 一个脚本两个 emit，或复用同一流做两个消费者 | 指出 RF-DSL-003；不能凭空加 cache/fork |
| B07 | lookup 响应为 `{}` 并要求当未命中 | 指出缺失 recordPath，RF-SRC-003；正常未命中应为 data:null |
| B08 | “请求结果超过 maxOutputRows 就返回前 N 条” | 指出默认超限是失败；截取须明确 limit 且保持业务语义 |
| B09 | “RPC 没确认幂等也开两次重试” | 指出 RF-CONFIG-002，不能只加 idempotent:true 绕过目录 |
| B10 | “只凭上述文档写一份可直接连接生产的脚本” | 说明缺少真实授权与接入契约，不能把示例占位配置宣称为生产可用 |

## 7. 一次演示怎样判定完成

脚本演示同时检查：扩展名与完整结构、源契约、合法 API、字段类型、关联和空值行为、失败/降级策略、预期结果。只有文字看起来像 Groovy 不算通过。

答疑演示同时检查：结论正确、引用能定位、没有补出不存在的功能、缺失信息时能说明边界。涉及错误码时应匹配文档中的精确分类。

本资料可做静态语法/契约审查及固定结果对照。若要验证编译、AST 白名单、真实请求、资源限制与运行隔离，必须补充实现了本规范的宿主和 mock 服务。固定样例计算或代码审阅不能替代实际运行证据。

## 8. AI 生成后直接导入平台

新场景建议使用 [16 多仓库存预警与补货汇总](16-新场景-库存补货演示与AI提示词.md)，其中提供完整的业务需求、接口样例、可复制提示词和验收值。AI 应同时读取 [平台用户手册](14-平台界面讲解指南.md) 与 [15 导入约定](15-脚本导入与可视化约定.md)。

输出完整 .groovy 文件，注释仅携带默认参数、样例响应与步骤标题。导入后平台从实际代码构建图、展示环节脚本和输入输出，并可单步演示。不要为适配界面发明新的 DSL 方法，也不要把预期结果放入注释冒充执行。

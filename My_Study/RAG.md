## 1. 总览

先建立整体认知。一次典型的 RAG 问答，检索模块通常同时跑两条线：

| 检索线 | 代表技术 | 擅长 | 短板 |
| --- | --- | --- | --- |
| 词法（lexical） | BM25（及其变种） | 精确词项匹配、专有名词、代码、ID、稀有词 | 不懂同义/近义/语义 |
| 语义（semantic） | BGE-M3 稠密向量 | 语义相似、跨语言、长文本 | 对精确词项/数字/专名不敏感 |

两者互补，真实系统往往**都要**。BGE-M3 的特殊之处在于：它一个模型、一次前向，同时给出稠密、稀疏、多向量三种表示——其中稀疏部分本质上就是"可学习的 BM25"。下面逐个拆解。

## 2. BM25

### 2.1 是什么

- 全称 **Best Matching 25**，又称 **Okapi BM25**，1990 年代由 Robertson、Walker 等在 Okapi 信息检索系统中提出。
- 一种**概率检索模型**下的相关度排序算法，用于计算"查询 Query 与文档 Doc 的相关性得分"。
- 是 Lucene / Elasticsearch / OpenSearch 等搜索引擎的**默认排序算法**，也是 RAG 词法检索的标准基线（baseline）。
- 是在 TF-IDF 思想上的改进：TF-IDF 只是词频×逆文档频率的启发式，BM25 把它改造成概率框架下的打分，并显式处理了**词频饱和**和**文档长度归一化**两个问题。

### 2.2 核心公式

对查询 Q 中的每个词项 qi，累加它在该文档上的得分：

```
Score(Q, D) = Σ_i  IDF(qi) ×  [ TF(qi,D) × (k1 + 1) ]
                        ─────────────────────────────
                        TF(qi,D) + k1 × (1 - b + b × len(D)/avgdl)
```

逐项含义：

| 符号 | 含义 | 说明 |
| --- | --- | --- |
| TF(qi,D) | 词项 qi 在文档 D 中的词频 | 出现越多越相关，但会"饱和" |
| IDF(qi) | 逆文档频率 | 越稀有的词权重越高，公式常见取 log(N/df_i) |
| k1 | 词频饱和参数 | 典型 1.2 ~ 2.0；越大，重复出现的词贡献衰减越慢 |
| b | 长度归一化系数 | 典型 0.75；越大，文档长度影响越大（越长越惩罚） |
| len(D) / avgdl | 文档长度 / 平均文档长度 | 长文档中词频会被稀释 |

关键直觉：
- **词频饱和**：词出现 3 次和出现 30 次，相关度不应线性翻 10 倍，得分增长逐渐放缓。
- **长度归一化**：同一词在一篇短文中出现，比在一篇长文中出现更能说明主题。
- **IDF 稀有度**：匹配到"罕见词"比匹配到"的、了"更有区分力。

### 2.3 特点与适用

- 优点：可解释、快、无需训练、对**精确词项 / 专有名词 / 代码 / 数字 / 用户习惯词**非常有效。
- 局限：**完全基于词面匹配**，无法理解同义改写、一词多义、语序差异——"苹果公司"和"库克任职的公司"对它来说是零重叠。
- 变种：
  - **BM25F**：对文档不同字段（标题/正文/标签）加权。
  - **BM25S**（2024，arXiv:2407.03618）：索引时贪心预计算 BM25 得分的稀疏矩阵实现，比主流 Python 实现快达 500×。

## 3. RAG

### 3.1 是什么

- 全称 **Retrieval-Augmented Generation（检索增强生成）**，核心一句话：**先搜再答**。
- 大模型不只用自己"背下来"的参数知识回答，而是先从外部知识库检索相关片段，把片段作为上下文喂给 LLM，再生成答案。

### 3.2 解决什么问题

| 问题 | 传统 LLM | RAG |
| --- | --- | --- |
| 知识截止日期 | 训练后就不知道新知识 | 随时可检索最新资料 |
| 幻觉 | 凭记忆编造 | 基于检索到的原文生成，可溯源 |
| 私有/领域数据 | 无法访问企业内网数据 | 检索企业知识库 |
| 成本 | 微调/重训昂贵 | 免重训，检索即可更新知识 |

### 3.3 典型流程（Index → Retrieve → Generate）

1. **索引（Index）**：把知识库文档**切分**成块（chunk）→ 用嵌入模型（如 BGE-M3）向量化 → 同时构建**倒排索引**（供 BM25）和**向量索引**（供语义检索）存入 Milvus / Elasticsearch 等。
2. **检索（Retrieve）**：用户 query 同样向量化，混合检索命中 Top-K 相关片段。
3. **生成（Generate）**：把 query + 检索片段拼进 Prompt，LLM 据此生成带依据的回答。

```
[知识库文档] --切分--> [chunk] --嵌入(BGE-M3)--> [dense向量+sparse向量]
                                        |
[用户问题] --嵌入--> [query向量] ------> 混合检索(BM25 + 向量)
                                        |
                                        v
                        [Top-K 相关片段] --注入--> [LLM] --> [答案]
```

### 3.4 RAG 的检索方式

- **词法检索**：BM25，精确匹配。
- **语义检索（稠密）**：向量相似度（余弦/内积）。
- **混合检索（Hybrid）**：两者同时跑，再用 RRF 等融合算法合并排名（见第 6 节）。

## 4. Wiki

### 4.1 在 RAG 语境下的含义

"Wiki" 在检索/Agent 场景下通常指**知识库（Knowledge Base）**，可作两层理解：

- **维基百科式公开知识库**：海量半结构化条目，是 RAG 系统常用的"开箱即用"知识源之一；Wiki 条目天然有标题、目录、引用，便于切分与溯源。
- **企业内部 Wiki / 文档库**：团队沉淀的私有知识（制度、流程、产品文档、项目资料），是 RAG 落地最有价值的知识来源。

### 4.2 Wiki 与 RAG 的关系

- **RAG 从 Wiki 检索增强生成**：LLM 不知道内部 Wiki 内容，RAG 把它变成可检索的外部记忆。
- **Wiki 是被检索的对象，不是检索器**：Wiki 提供"数据源"，BM25 / BGE-M3 提供"检索能力"，两者配合。
- **选型直觉**：公开/静态知识可用维基百科等现成语料；私有/动态知识必须自建 Wiki + RAG。

### 4.3 常见的"RAG vs Wiki"辨析

| 维度 | Wiki（知识库） | RAG |
| --- | --- | --- |
| 角色 | 知识载体 / 数据源 | 检索 + 生成的方法论 |
| 回答方式 | 人工/规则查条目 | LLM 基于检索片段自动生成 |
| 强项 | 结构清晰、权威、可编辑 | 自然语言问答、覆盖广、可溯源引用 |

实际生产中两者不是二选一，而是**Wiki 作为知识底座，RAG 作为访问它的智能入口**。

## 5. BGE-M3

### 5.1 是什么

- 全称 **M3-Embedding**，智源研究院（BAAI）2024 年 1 月发布的通用向量模型（论文 arXiv:2402.03216）。
- **M3 = Multi-Linguality（多语言）+ Multi-Granularity（多粒度）+ Multi-Functionality（多功能）**。
- 参数约 **568M**，一个编码器、一次前向，同时输出三种检索表示。

### 5.2 三大能力（三个 M）

| M | 能力 | 要点 |
| --- | --- | --- |
| **多语言** | 支持 100+ 种语言 | 学一个统一语义空间，支持同语言检索 + 跨语言检索 |
| **多粒度** | 短句到 8192 token 长文档 | 可处理句子、段落、篇章、文档不同粒度 |
| **多功能** | 稠密 + 稀疏 + 多向量 | 一站式支撑三种检索范式 |

### 5.3 三种输出（核心卖点）

1. **稠密向量（Dense）**：定长向量（如 1024 维），语义相似度检索，适合召回语义相近文本。
2. **稀疏表示（Sparse）**：形如 `{token_id: 权重}` 的字典，**本质是"学出来的关键词权重"**——由模型学习哪些词重要，而不是像 BM25 那样纯靠统计。行为上类似"可训练的 BM25"，解决稠密向量对精确词项不敏感的问题。
3. **多向量（Multi-Vector）**：ColBERT 风格，保留每个 token 的向量做"晚期交互"（late interaction）细粒度打分，兼顾精度。

> 一句话理解：**BGE-M3 = 语义检索（dense）+ 可学习的关键词检索（sparse）+ 精细交互检索（multi-vector）**，三合一。

### 5.4 在检索链路中的位置

- 作为 RAG 的**嵌入模型**，在索引阶段和 query 阶段把文本变成向量。
- 因其同时产出 dense + sparse，一个模型就能支撑**混合检索**，无需另配 BM25 + 一个语义模型两套系统。
- 常与 Milvus（支持 dense + sparse 混合检索、RRF 融合）配套使用。

## 6. 混合检索

### 6.1 为什么混合

- 单靠**稠密向量**：擅长语义，但同义词改写、抽象问题表现好；对专有名词、代码、编号、精确数字不敏感。
- 单靠**BM25**：精确词项强，但不懂语义改写，容易漏掉"意思相同但用词不同"的文档。
- **混合检索（Hybrid Search）= BM25 + 语义向量 同时跑，合并结果**，取长补短，召回率和相关性都更稳。

### 6.2 如何融合排名

常见算法 **RRF（Reciprocal Rank Fusion，倒数排名融合）**：

```
score(d) = Σ 1 / (k + rank_i(d))     // k 为常数，通常取 60
```

对每个文档，把它在**每条检索线**中的名次取倒数累加；名次越靠前，贡献越大。这样避免不同检索线得分尺度不一致的问题，纯按排名融合。

### 6.3 BGE-M3 如何简化混合

传统混合要维护两套系统：BM25（倒排索引）+ 语义模型（向量索引）。而 BGE-M3 一次给出 dense + sparse：
- **sparse 输出** → 直接喂给稀疏检索/倒排检索（替代或补充 BM25）；
- **dense 输出** → 喂给向量检索；
- 两者融合即可，**一个模型完成词法与语义两条线**。

## 7. 横向对比与选型建议

### 7.1 BM25 vs BGE-M3

| 维度 | BM25 | BGE-M3（dense） | BGE-M3（sparse） |
| --- | --- | --- | --- |
| 原理 | 统计词频+稀有度 | 神经网络语义向量 | 神经网络学习词权重 |
| 是否需要训练 | 否 | 是（预训练+微调） | 是（随模型训练） |
| 语义理解 | 无 | 强 | 中（偏关键词但可学习） |
| 精确词项/专名/数字 | 强 | 弱 | 强（可学习） |
| 跨语言 | 不支持 | 100+ 语言 | 随模型 |
| 可解释性 | 高 | 低 | 中 |
| 资源 | 极轻 | 较重（568M 模型） | 较重 |

### 7.2 怎么选

| 场景 | 推荐 |
| --- | --- |
| 代码/ID/编号/专有名词检索，要求可解释 | 偏 BM25 |
| 语义相似、同义改写、跨语言、长文档 | 偏 BGE-M3 dense |
| 通用知识库问答，追求稳定召回 | 混合：BGE-M3（dense+sparse）+ RRF，或 BGE-M3 + BM25 双线 |
| 轻量、无 GPU、极致延迟 | BM25（Lucene/ES） |

### 7.3 一条推荐链路

```
知识库(Wiki) --切分--> chunk
   ↓ 索引：BGE-M3 一次前向产出 dense + sparse
   ↓ 存储：Milvus（dense向量 + sparse向量），可另建倒排索引供 BM25
用户query --BGE-M3嵌入--> dense + sparse
   ↓ 混合检索：BM25 / sparse + dense 同时跑
   ↓ 融合：RRF
   ↓ Top-K 片段注入
   ↓ LLM 生成 + 溯源引用
```

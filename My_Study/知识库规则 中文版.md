# 大模型知识库（LLM Wiki）

一种用大模型搭建个人知识库的模式。这是一份思路文件，交给你的大模型智能体使用。目录结构和 AGENTS.md 必写条款按下方「搭建规格」执行，其余细节由智能体提出建议，你批准后再完善。

## 搭建规格（必须照做）

按下面的结构创建，文件夹和文件名一字不改，不要改成纯英文：

```text
AGENTS.md
原始资料 raw/
├── 已摄入/
└── 附件 assets/
知识库 wiki/
├── 目录 index.md
├── 日志 log.md
├── 综述 overview.md
├── 资料摘要 sources/
├── 实体 entities/
├── 概念 concepts/
└── 分析 analyses/
报告 reports/
```

- 只创建以上文件夹和文件。不要创建脚本、模板或其他文件夹，不要在文件夹里放说明文件，不要初始化 git，不要修改 Obsidian 设置。
- 所有页面内容用中文。
- 不预设研究领域。领域根据摄入的资料归纳，写在 `综述 overview.md` 里，随资料更新。
- 页面文件名用中文。有通行中文译名的专有名词，写成「中文名 原名」，如 `安德烈·卡帕西 Andrej Karpathy.md`；没有通行中文名的保留原名，如 `OpenAI.md`。资料摘要页用资料标题命名，不加序号，不与原文文件同名，否则链接会指向原文。
- 页面属性里，标签必须写作 `tags`，别名必须写作 `aliases`，这样 Obsidian 才能识别；其他属性名可以用中文。
- 规则文件 `AGENTS.md` 放在仓库根目录，控制在 8000 字符以内。

### AGENTS.md 必须写明的条款

生成 AGENTS.md 时，以下条款逐条写入，不得省略或改弱：

1. **写入位置**：摘要写进 `资料摘要 sources/`，实体页写进 `实体 entities/`，概念页写进 `概念 concepts/`，分析写进 `分析 analyses/`。写文件前先列出现有目录，只写进已有文件夹。
2. **规则由用户批准**：智能体不得自行修改 AGENTS.md。想改规则时，在对话或摄入报告里提出建议，用户同意后再改。
3. **建页标准**：原文单独成节或重点论述的方法、人物、机构、产品，建独立页面；只被提及、引述或作为示例出现的不建页，写进相关页面。
4. **事实纪律**：页面里的事实和引述都要能在原文找到；原文没说的标「非原文」，自己的推断、归纳和解读也算非原文。工作记忆和旧日志不能当事实来源，引用前重新核实。
5. **标签清单**：只用 `资料摘要`、`实体/人物`、`实体/机构`、`实体/产品`、`概念`、`分析`、`综述`、`索引`、`日志`、`摄入报告`、`体检报告`；要新增标签，先征得用户同意。
6. **收尾自检**：每次摄入的页面全部写完后、把资料移入 `已摄入/` 之前自检：对照目录结构检查文件位置；对照原文核对每一条事实陈述，不只核对引号里的原话，找不到出处的删掉或标「非原文」；列出未解析的链接。结果写进日志或报告，自检通过后再移动资料。

本文件没写的内容，不要自行添加到 AGENTS.md；确实需要补充的，在对话里单独列出来，由你批准后再加。

## 核心思路

- 大模型逐步搭建并维护一个**持久的知识库**：一套结构化、相互链接的 Markdown 文件，位于你和原始资料之间。
- 加入新资料时，大模型读完资料、提取关键信息，并整合进已有知识库：更新实体页，修订主题摘要，标出新旧说法的矛盾，强化或修正综合结论。
- 知识只编译一次，之后保持最新，而不是每次提问都重新推导。每加入一份资料、每提一个问题，知识库都会更丰富。
- 分工：知识库由大模型写和维护，包括摘要、交叉引用、归档、记录；你负责挑选资料、指导分析、提出问题。

## 架构

**原始资料 raw/**：你挑选的原始文档，如文章、论文、图片、数据文件，是事实的最终依据。大模型不修改内容、不改名、不删除；唯一允许的操作是把摄入完成的资料移入 `原始资料 raw/已摄入/`。

**知识库 wiki/**：大模型生成的 Markdown 文件，包括资料摘要、实体页、概念页、分析页（对比、问答沉淀）和综述（概览与综合结论）。这一层完全由大模型负责：创建页面，新资料到来时更新页面，维护交叉引用，保持内容一致。

**规则文件 AGENTS.md**：告诉大模型知识库的结构、约定，以及摄入、查询、维护时要遵循的流程。有了它，大模型才是守纪律的知识库维护者，而不是普通的聊天机器人。使用中由大模型提出修改建议，你批准后再修改。

## 操作

**摄入**：你把新资料放进 `原始资料 raw/`，让大模型处理。`原始资料 raw/` 中不在 `已摄入/` 里的文件，就是待摄入的资料。流程：读取资料 → 和你讨论要点 → 在 `资料摘要 sources/` 写一页摘要 → 更新相关的实体页和概念页 → 影响全局判断时，更新 `综述 overview.md`（领域、综合结论、矛盾汇总） → 更新目录 → 收尾自检 → 在日志追加一条记录 → 把资料移入 `原始资料 raw/已摄入/`。移动是最后一步，页面全部写完、自检通过后再移动。一份资料可能牵动 10 到 15 个页面。

**批量摄入**：你说「摄入新资料」，或定时任务触发时，大模型一次处理全部待摄入资料。你可能不在场，所以全程不讨论、不等待确认：

- 每份资料按摄入流程处理，跳过"和你讨论要点"这一步。
- 拿不准的地方按保守方式处理：不确定是否要建新页，就先不建；新旧说法冲突，就标注矛盾、两边都保留，不要自行化解或合并。这些都记入报告，等你事后判断。
- 读不了的文件留在原处不动，记入报告。
- 全部完成后，在 `报告 reports/` 写一份 `YYYY-MM-DD 摄入报告.md`，写明：处理了哪些资料、新建和更新了哪些页面、发现的矛盾、需要你确认的事项、跳过的文件及原因。
- 在日志追加一条批量摄入记录，链接这份报告。

**查询**：你向知识库提问，大模型搜索并阅读相关页面，给出带引用的答案。答案可以是页面、对比表、幻灯片、图表等形式。**好的答案要作为新页面存进 `分析 analyses/`**，让探索的成果也能积累下来。

**体检**：定期让大模型检查知识库。查出的问题由大模型直接修好，不用等你确认；修完写一份体检报告。这样知识库随规模增长也能保持健康。

检查项：

- 页面之间的矛盾
- 已被新资料取代的过时说法
- 没有入链的孤立页
- 被提到但缺少独立页面的重要概念
- 缺失的交叉引用
- 可以通过网络搜索补上的数据空白
- 页面内容与原文不符，或推断没有标「非原文」
- 链接指向了错误的文件

修复方式：

- 断链、链接指错文件、缺失的交叉引用、页面属性缺漏、目录与页面不一致：直接改正。
- 内容与原文不符：改回原文说法；推断没标的，补标「非原文」。
- 过时说法：按新资料更新，并注明被哪份资料取代。
- 孤立页：补上入链。
- 缺少独立页面的概念：符合建页标准的直接建页。
- 页面之间的矛盾：以原文为准改正；如果是资料之间说法不同，两边保留、标注清楚，写进综述的矛盾汇总，不要自行化解或合并。
- 数据空白：网络检索的结果单独存进 `分析 analyses/`，标明出处和「非原文」，不写进其他页面。
- 以上修复只改 `知识库 wiki/` 里的页面；原始资料和 AGENTS.md 不动，对规则的修改建议写进报告。
- 修完按收尾自检的方法复查一遍。

**体检报告**：在 `报告 reports/` 写一份 `YYYY-MM-DD 体检报告.md`，写明：查出了哪些问题、每个问题怎么修的、改了哪些页面、修不了的问题及原因，以及值得研究的新问题和值得寻找的新资料。在日志追加一条体检记录，链接这份报告。

## 目录与日志

**目录 index.md**：按内容组织的清单。每个页面附链接和一句话摘要，可加日期、来源数量等信息，按类别（实体、概念、资料等）分组。每次摄入后更新；回答问题时先读目录，再读具体页面。约 100 份资料、几百个页面的规模下，只靠目录就够用。

**日志 log.md**：按时间排列、只追加的记录，记下每次摄入、查询、体检。每条用统一前缀开头，例如 `## [2026-04-02] 摄入 | 文章标题`，这样可以用 `grep "^## \[" "日志 log.md" | tail -5` 查看最近 5 条。

## 可选工具与设置

以下内容在用户提出需要时再做，搭建时不要创建。

- **搜索**：知识库变大后，目录不够用时，可以接入本地 Markdown 搜索引擎（如 [qmd](https://github.com/tobi/qmd)，有命令行和 MCP 服务），或让大模型写一个简单的搜索脚本。
- **收集资料**：用 Obsidian Web Clipper 把网页文章转成 Markdown，放进原始资料。
- **图片存到本地**：在 Obsidian 设置 → 文件与链接中，把附件文件夹设为 `原始资料 raw/附件 assets/`，再给"下载当前文件的附件"绑定快捷键。大模型读取带图片的资料时，先读文字，再单独查看图片。
- **页面属性**：大模型在页面开头写 YAML 属性（标签、日期、来源数量），可用 Dataview 插件生成动态表格和列表。
- **版本管理**：知识库就是一个 Markdown 文件夹，可以用 git 管理版本。

## 说明

除「搭建规格」外，规则约定、页面格式和工具都可以按你的领域、偏好和所用的大模型调整：由大模型提出建议，你批准后再修改。正确的用法是把它交给你的大模型智能体，一起落成适合你的版本。

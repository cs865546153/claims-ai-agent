**一句话总结：Wiki 是 RAG 系统的「原始内容数据源」，向量数据库是「向量索引的存储与检索引擎」，二者是「数据原料」与「存储 / 检索工具」的上下游对应关系，共同支撑检索阶段的三条召回线：语义召回（BGE-M3 向量）、词法召回（BM25）与结构召回（标题/章节等元数据）。**

---

### 一、本质定位与层级区别

二者完全不在同一个层面，是数据和工具的关系：

- **Wiki（维基百科）**：属于**数据层**，是纯文本内容来源，提供原始的、人类可读的自然语言文档（词条、段落、章节）。它本身不具备向量计算、相似度检索的能力。
- **向量数据库**：属于**索引 / 检索层**，是专门用来存储向量、执行向量相似度计算的基础设施。它本身不生产原始内容，核心存储的是文本向量化后的数值向量，以及对应原始文本的标识 / 元数据。

---

### 二、全链路中的协作关系（结合混合检索链路）

#### 1. 离线构建阶段：Wiki 是源，向量数据库是目标

数据流向是单向的：从 Wiki 流向向量数据库。

1. 先对 Wiki 原始词条做**文本切片**（按段落 / 章节拆分为 512/1024 token 左右的语义块）
2. 用 BGE-M3 等 Embedding 模型，把每一块 Wiki 文本转换成**稠密向量 / 稀疏向量**
3. 把生成好的向量 + 对应 Wiki 片段的原文 / ID / 词条链接等元数据，写入向量数据库并构建向量索引

>
> 关键对应：同一份 Wiki 切片会同时构建**多条检索索引**，各索引通过**切片 ID（chunk ID）一一对应**：
>
>
> - 一套是 **BM25 倒排索引**（存于 Elasticsearch、Solr 等引擎中）——注意它是对切片原文**分词统计**构建的，**不经过任何 Embedding 模型**
> - 一套是 **向量索引**（存于向量数据库中），用于语义召回
> - BGE-M3 输出的**稀疏向量**则对应一份稀疏向量索引（如 Milvus 的 Sparse Vector 字段），它是模型学出来的词权重，**不等于 BM25**
>
> 常见架构二选一：
>
> - **方案 A（传统混合）**：BM25（统计倒排索引，词法线）+ BGE-M3 稠密向量（语义线），两条独立检索线
> - **方案 B（单模型混合）**：BGE-M3 一次前向同时输出 dense + sparse，两路都进向量数据库（Milvus 2.4+ 官方教程的标准做法），无需另配 BM25 引擎
> - 无论哪种方案，BGE-M3 稀疏向量与 BM25 都是**并列的两种词法召回手段**（learned sparse vs 统计 BM25），不能混为一谈

#### 2. 在线检索阶段：向量数据库负责 “找相似”，Wiki 内容负责 “供原文”

1. 用户输入 Query，先用 BGE-M3 把 Query 转换成查询向量
2. 向量数据库接收查询向量，执行**近似最近邻搜索（ANN）**，返回（近似）相似度最高的 Top-K 条向量对应的元数据；通常切片原文就作为元数据 Payload 一并返回，无需再单独拉取
3. 返回的 Wiki 原始文本片段，与 BM25 / 稀疏检索召回的 Wiki 片段汇合，去重后进入后续的 RRF 融合、Rerank 重排序，最终送入 LLM 生成答案

> 参考：ANN 是近似检索（如 HNSW / IVF 等索引结构），返回的是“近似最相似”的 Top-K，精度与召回率受 ef / nprobe 等参数影响，并非精确全局最优。

---

### 三、常见误区澄清

1. **向量数据库不替代 Wiki**
向量数据库的核心是存向量，Wiki 原文通常只作为元数据附带存储；完整的 Wiki 全量内容一般会单独存在文档存储、对象存储或搜索引擎中，向量数据库只保留检索必需的片段和标识。
2. **不是只有 Wiki 才能进向量数据库**
Wiki 只是众多数据源中的一种，PDF、网页、业务文档、工单记录等任何文本，都可以向量化后存入向量数据库。
3. **BGE-M3 稀疏向量与 BM25 是两种东西**
   BGE-M3 输出的稀疏向量是**模型学出来的词权重**（learned sparse，类似 SPLADE），而 BM25 是**纯统计打分**（词频 × IDF，不涉及模型）。两者是并列的两种词法召回手段：BGE-M3 稀疏向量可存入支持稀疏索引的向量数据库（如 Milvus 2.4+），或用 Elasticsearch 8.11+ 的 `sparse_vector` 字段承载；BM25 则依赖传统倒排索引引擎（ES 是 Lucene 的默认相似度算法）。

---

### 四、索引层的分工：角色 ≠ 产品

前文把「向量数据库」和「BM25 引擎」并举，容易让人以为两者是固定的两个产品。更准确的表述是：索引层只按**功能**划分（词法线 vs 语义线），具体产品可以互相兼任：

```
【索引层·双路】的落地可以三种组合:

组合①(单引擎 all-in-one,如 ES 单栈):
  ES 一个产品里同时建 BM25 倒排索引 + dense_vector(HNSW) 向量索引
  → ES 8.0+ 支持 dense_vector(ANN 检索)、8.11+ 支持 sparse_vector
  → 一个产品覆盖双路，不再需要额外的向量数据库

组合②(单向量库 all-in-one,如 Milvus 单栈,方案 B 的标准落地):
  Milvus 一个产品里同时建 dense 索引 + sparse 索引(BGE-M3 双路)
  → Milvus 2.4 支持 sparse 向量;2.5 甚至内置了 BM25(Full-Text Search)

组合③(双引擎,各司其职):
  ES 专门跑 BM25 + Milvus 专门跑向量,召回后按 chunk ID 对齐融合
```

关键结论：

- **BM25 用 ES 承载是本职**：自 Lucene 5.0 起 BM25 就是 ES 的默认相似度算法；
- **向量检索用 ES 也可以**：ES 8.0+ 的 `dense_vector` 原生支持 ANN，此时 ES 本身就是一个向量数据库，**不存在「向量数据库底层用 ES」的说法，而是 ES 直接兼任向量数据库**；
- 传统对举「Milvus = 向量库 / ES = 词法引擎」只是常见用法，**能力边界正在互相渗透**。

选型直觉：

| 场景 | 建议 |
| --- | --- |
| 规模小、团队已熟悉 ES、不想引入新产品 | 组合①（ES 单栈），最省运维 |
| 追求 dense+sparse 单模型混合的召回效果、规模大 | 组合②（Milvus 2.4+ + BGE-M3） |
| 已有 ES 深度用 BM25，向量量级大到需要专门向量库 | 组合③（双引擎） |

### 五、本项目实际实现：BGE-M3 向量召回、BM25、元数据召回是什么，怎么协作

> 本节讲的是**本仓库当前代码**，不是通用理论。对应实现主要在 `tools/knowledge_rag.py`、`tools/vector_store.py`、`tools/rerank.py` 和 `tools/rag_retrieval.py`。

#### 5.1 先给结论

这三路不是“主检索 + 副检索”的关系，而是**三个并列的候选生成器**。它们各自从不同角度找候选，最后再融合、去重、精排：

| 召回线 | 一句话解释 | 看什么信号 | 本项目实现 | 权重 |
| --- | --- | --- | --- | --- |
| BGE-M3 向量召回（dense） | 把 query 和文档都变成向量，找“意思相近”的片段 | 语义相似度 | BGE-M3 生成 1024 维向量 → Milvus ANN 检索 | 0.55 |
| BM25 召回（bm25） | 传统关键词打分，找“字面词命中”的片段 | 词频、逆文档频率、文档长度 | `BM25Okapi` + 中文单字/双字分词 | 0.30 |
| 元数据召回（metadata） | 只看标题、章节、主题、来源，找“目录/标题对得上”的片段 | 结构化字段匹配 | `MetadataIndex` 对 metadata 打分 | 0.15 |

对应的代码入口在 `tools/knowledge_rag.py`：

```python
self._retriever = MultiRouteRetriever(
    [
        RetrievalRoute('dense', weights[0], self._search_vector),
        RetrievalRoute('bm25', weights[1], BM25Index(self.documents).search),
        RetrievalRoute('metadata', weights[2], MetadataIndex(self.documents).search),
    ],
    candidate_multiplier=candidate_multiplier,
    reranker=reranker,
)
```

权重定义在 `tools/knowledge_rag.py` 顶部：

```python
DEFAULT_WEIGHTS = (0.55, 0.30, 0.15)
```

#### 5.2 BGE-M3 向量召回：解决“意思相近但用词不同”

**是什么**

BGE-M3 是一个 Embedding 模型。它把一段文本压缩成一个固定长度的稠密向量（本项目是 **1024 维**）。语义越接近的文本，向量在空间里的方向/距离越接近。

- 用户问：“亏钱了怎么办”
- 文档写：“本金出现波动，甚至损失部分或全部本金”

两句话几乎没有共同关键词，但向量距离会比较近，所以能被向量召回捞出来。

**本项目怎么用**

1. 离线建索引：`load_investment_documents()` 把 Wiki 按 `##` 章节切分，再用 `RecursiveCharacterTextSplitter` 切成约 600 字、重叠 80 字的 chunk；
2. 每个 chunk 通过本地 `scripts/embed_server.py` 的 `/v1/embeddings` 调 BGE-M3，生成归一化向量；
3. 向量写入 Milvus（本地是 `.data/milvus.db`，集合 `investment_wiki`），索引为 `IVF_FLAT`，度量 `L2`；
4. 在线检索时，query 同样走 BGE-M3 变成查询向量，Milvus 做 ANN（近似最近邻）搜索，返回 Top-K 候选。

对应代码：`tools/vector_store.py` 的 `KnowledgeVectorStore.search()`：

```python
return self.store.similarity_search(
    query,
    k=k,
    expr=build_filter_expr(filters),
)
```

**擅长**

- 同义改写、口语化提问；
- 概念解释、因果关系、总结类问题；
- 用户不知道专业术语，只描述现象时。

**不擅长**

- 精确的产品代码、保单号、日期、费率数字；
- 生僻专有名词；
- 很短、很泛的 query（向量区分度不够）。

#### 5.3 BM25 召回：解决“关键词必须精确命中”

**是什么**

BM25 是纯统计的关键词打分算法，不经过任何模型。它主要看三件事：

1. 查询词在文档里出现了几次（TF）；
2. 这个词在整个语料里有多稀有（IDF，越稀有越值钱）；
3. 文档长度（长文档要适当降权，避免靠“字多”占便宜）。

可以把它理解成“升级版关键词搜索”：不是简单数命中次数，而是会给稀有词、精确词更高的权重。

**中文怎么分词**

BM25 原本面向空格分词的语言。中文没有空格，所以项目里用了 `chinese_tokens()`：

`tools/rag_retrieval.py:115`

```python
def chinese_tokens(text: str) -> list[str]:
    units = re.findall(r'[a-zA-Z0-9_]+|[\u4e00-\u9fff]', text.lower())
    return units + [a + b for a, b in zip(units, units[1:]) if len(a) == len(b) == 1]
```

例如“投资基础知识”会被切成：

- 单字：`投`、`资`、`基`、`础`、`知`、`识`
- 相邻双字：`投资`、`资基`、`基础`、`础知`、`知识`

这样做的好处是不依赖额外分词器，坏处是会产生一些无意义双字（如“资基”），所以 BM25 结果还需要后面的融合和精排来纠偏。

**建索引时看哪些字段**

`BM25Index._index_text()` 把标题、章节、主题和正文拼在一起：

```python
fields = ' '.join(
    str(metadata.get(key) or '')
    for key in ('title', 'chapter', 'topic')
)
return f'{fields} {document.page_content}'
```

注意一个实现细节：BM25 打分时用了标题/章节，但最终过滤候选时要求 query token 与**正文**有交集：

```python
if query_tokens.intersection(chinese_tokens(document.page_content)):
    results.append(document)
```

所以只在标题里命中、正文完全不含查询词的片段，不会从 BM25 这条路出来（但可能从元数据召回出来）。

**擅长**

- 产品名、条款名、费用名：“申购费”“赎回费”“管理费”；
- 精确短语：“沪深 300”“风险等级 R3”；
- 代码、数字、日期、专有名词；
- 用户明确说出文档里的原词时。

**不擅长**

- 同义改写：“手续费” vs “费用”；
- 跨句语义：“市场跌了要不要卖”；
- 错别字、口语化表达。

> 本项目用的是内存版 BM25；如果换成 ES，查询流程、`size` 参数和“先 100 再 10”的误解见 5.8。

#### 5.4 元数据召回：解决“标题/章节直接对得上”

**是什么**

元数据召回完全不看正文语义，也不做全文词频统计，只看每条 chunk 的结构化字段：

- `title`：文档标题
- `chapter`：章节标题
- `topic`：主题
- `source`：来源路径

它更像“查目录”：用户问“基金费用”，如果某篇文档的标题或章节就叫“基金费用”，这条应该优先被拿出来。

**打分方式**

`MetadataIndex.search()` 的逻辑是：

```python
exact = sum(1 for field in fields if query_lower and query_lower in field)
overlap = len(query_tokens & field_tokens) / len(query_tokens)
score = exact * 3.0 + overlap
```

- 整个 query 原样出现在某个字段里：`exact` 加 1，权重 3.0（强信号）；
- 否则按 query token 与字段 token 的重合比例打分；
- 只保留 `score > 0` 的候选，按分数降序、原顺序升序返回。

**擅长**

- “基金费用”“资产配置”“风险适当性”这种和章节标题高度一致的 query；
- 用户明确问某篇文档/某个主题；
- 作为向量召回和 BM25 的“结构先验”补充。

**不擅长**

- 正文里的细节问题；
- 标题很泛、很多文档共用同一个章节名时；
- 只看字段，无法理解具体语境。

**它不是 metadata filter**

项目里的 `filters` 是另一套机制：按 `domain`、`source` 等字段做**硬过滤**（不满足直接排除）。元数据召回是**软打分**，是把标题/章节相关的片段排前面，不是排除其他片段。

#### 5.5 三路怎么协作：并行召回 → 去重 → 加权 RRF → 精排

完整流程：

```text
用户 query："投资基础知识"
        │
        ├─ dense 路：query → BGE-M3 → Milvus ANN ─────────→ 16 条候选
        ├─ bm25 路：query → 中文分词 → BM25Okapi ──────────→ 16 条候选
        └─ metadata 路：query → 标题/章节/主题/来源打分 ───→ 16 条候选
        │
        ▼
   按 doc_id 去重（同一个 chunk 被多路命中只保留一份）
        │
        ▼
   加权 RRF 融合：score(d) = Σ w_r / (60 + rank_r(d))
        │
        ▼
   融合候选按分数排序（实测 "投资基础知识" 融合后 26 条）
        │
        ▼
   取前 12 条（k × 3）→ BGE-Reranker Cross-Encoder 精排
        │                    └─ 服务不可用时降级为 LexicalReranker
        ▼
   取最终 top_k = 4 条 → 拼成带引用的上下文 → 交给投资回答模型
```

**第一步：三路各取多少条**

`MultiRouteRetriever` 里：

```python
candidate_k = max(k, k * self.candidate_multiplier)
```

本项目 `investment_rag_top_k = 4`，`rag_candidate_multiplier = 4`，所以：

```text
candidate_k = 4 × 4 = 16
```

也就是每一路先各取 16 条，而不是直接只取 4 条。这样做的目的是给后面的融合和精排留足候选，避免第一轮就把好片段漏掉。

**第二步：为什么用 RRF，而不是把三路分数直接相加**

三路分数的量纲完全不同：

- 向量路返回的是 L2 距离（越小越相似）；
- BM25 返回的是无上界的相关度分数（越大越相关）；
- 元数据返回的是 0～3 左右的启发式分数。

直接相加没有可比性，还会被某一路的数值范围带偏。RRF（Reciprocal Rank Fusion）只看**排名**，不看原始分数：

```text
score(d) = Σ_{r ∈ 命中 d 的召回线} w_r / (rrf_k + rank_r(d))
```

- `rrf_k = 60`，是一个平滑常数，避免第 1 名和第 2 名差距过大；
- `rank_r(d)` 是文档 d 在第 r 路里的名次，从 1 开始；
- `w_r` 是这一路的权重，本项目是 dense 0.55、bm25 0.30、metadata 0.15；
- 同一个文档被多路命中时，分数会累加，相当于“多个评委都推荐它”。

举个直观例子（假设权重如本项目）：

| 文档 | dense 名次 | bm25 名次 | metadata 名次 | RRF 分数（约） |
| --- | --- | --- | --- | --- |
| A | 1 | 5 | 2 | 0.55/61 + 0.30/65 + 0.15/62 ≈ **0.01605** |
| B | 1 | — | — | 0.55/61 ≈ **0.00902** |
| C | — | 1 | 1 | 0.30/61 + 0.15/61 ≈ **0.00738** |

A 虽然只在 dense 排第 1，但同时被 BM25 和元数据认可，所以总分最高。
这就是三路协作的核心：**不是谁替代谁，而是让不同信号互相验证；多路共识的片段优先。**

**第三步：融合之后为什么还要 Rerank**

RRF 解决的是“多路结果怎么合并”，它仍然只是**粗排**。真正判断“query 和这段正文是否真的相关”的，是 Rerank 层：

- RRF：只看名次，不看 query 和正文的具体语义；
- Rerank：把 `query + 候选正文` 成对送进 Cross-Encoder，逐条打相关性分数。

本项目把融合后的前 12 条送入 `bge-reranker-base`，再取前 4 条。
所以完整的层次是：

```text
召回（三路并行，负责“别漏”）
    → RRF 融合（负责“合并、去重、粗排”）
    → Rerank（负责“精排”）
    → 最终 Top-K（负责“控制上下文长度”）
```

**第四步：某一路挂了怎么办**

三路之间是解耦的，单路失败不会阻断整个链路：

- BGE-M3/Milvus 不可用：dense 返回空，BM25 + metadata 继续工作，结果标记 `degraded=true`；
- 某一路抛异常：记录到 `route_errors`，其他路继续；
- Rerank 服务不可用：降级到 `LexicalReranker`，结果标记 `rerank_fallback=true`。

这也是为什么 `KnowledgeBase.retrieve()` 的返回里会有：

```text
vector_ready / degraded / vector_error / retrieval.route_hits / retrieval.route_errors
```

这些字段就是给排障用的。

#### 5.6 结合“投资基础知识”这次请求看

实测 `top_k=4` 时：

```text
candidate_k = 16
route_hits  = dense 16 / bm25 16 / metadata 16
fused_count = 26
reranked    = true
reranker    = FallbackReranker（内部优先调用 BGE-Reranker）
rerank_fallback = false
rerank_error = None
returned    = 4
```

说明三路都正常召回，RRF 也正常融合，最后一步由 `models/bge-reranker-base` 的
Cross-Encoder 完成精排。当前 `/v1/rerank` 健康可用；用相关文档 `基金有市场风险`
和不相关文档 `今天天气很好` 验证，得分分别约为 `0.996` 和 `0.00004`。

这也解释了一个容易误解的点：

> **BM25 是召回线，不是最终重排器。**
> 当前代码里没有“检索完再用 BM25 排一遍”的逻辑；BM25 的分数只用于产生自己的名次，然后转成 RRF 的 `1/(60+rank)` 贡献。

#### 5.7 三路召回速查表

| 你的问题特征 | 主要依赖哪一路 | 例子 |
| --- | --- | --- |
| 只描述现象、用词和文档不一样 | dense | “亏钱了怎么办”“市场跌了要不要卖” |
| 明确说出产品名、费用名、代码、数字 | bm25 + metadata | “申购费”“沪深 300”“R3 风险等级” |
| 问某个主题/章节 | metadata + dense | “基金费用”“资产配置”“投资基础知识” |
| 精确短语 + 语义解释混合 | 三路都用 | “基金的管理费和托管费有什么区别” |
| 生僻词、错别字、口语化 | dense 为主 | “那个管理费咋收的” |

一句话记忆：

```text
dense    = 按“意思”找
bm25     = 按“词”找
metadata = 按“目录/标题”找
RRF      = 三个结果按名次加权合并
rerank   = 合并后再逐条精读打分
```

#### 5.8 ES 里 BM25 到底怎么查询：是“先召回 100 条再打分”吗？

**结论：不是。**

很多人会把 ES 的查询理解成：

```text
ES 先返回 100 条
    → 再用 BM25 打分
    → 取前 10
```

这个理解把“候选生成”和“打分排序”拆成了两个先后阶段，但 ES 内部不是这样工作的。更准确的流程是：

```text
query 分词
    → 倒排索引找到“包含这些词”的候选 chunk
    → 对所有候选 chunk 用 BM25 打分
    → 按分数取前 N 条返回（N 由 size 控制）
```

BM25 打分发生在**返回之前**，不是 ES 先返回 100 条再打分。
“100 条”和“10 条”不是两个固定阶段，而是你设置的 `size` 参数。

##### 1. ES 内部到底发生了什么

假设知识库切片后，ES 里有 3 个 chunk：

```text
D1: 基金费用包括申购费、赎回费和管理费
D2: 基金收益与风险
D3: 股票交易规则
```

用户查询：

```text
基金费用
```

**第 1 步：query 分词**

ES 用 analyzer 把 query 切成词项：

```text
基金 / 费用
```

**第 2 步：查倒排索引**

ES 的倒排索引大致是：

```text
基金 → [D1, D2]
费用 → [D1]
风险 → [D2]
股票 → [D3]
```

查询词 `基金` 和 `费用` 的 posting list 合并后，候选 chunk 是：

```text
D1, D2
```

注意：**候选数量不是固定的 100**，而是取决于有多少 chunk 命中了 query 词。
可能只有 2 条，也可能有 10 万条。

**第 3 步：BM25 打分**

ES 对候选 chunk 逐个计算 BM25：

```text
D1: 命中“基金”和“费用”，且“费用”较稀有 → 高分
D2: 只命中“基金”，没有“费用” → 低分
```

BM25 会综合考虑：

- 词在 chunk 里出现几次（TF）；
- 词在整个语料里有多稀有（IDF）；
- chunk 长度（长度归一化）。

**第 4 步：取前 N 条返回**

```json
{
  "query": { "match": { "text": "基金费用" } },
  "size": 10
}
```

`size: 10` 表示最终返回 BM25 分数最高的 10 条。
如果你写 `size: 100`，就是返回前 100 条。

**ES 默认 `size` 就是 10。**
所以“先返回 100 再取 10”不是默认行为，而是你自己设置了两步。

##### 2. “先 100 再 10”什么时候成立？

它成立，但第二阶段通常**不是 BM25**，而是 Reranker。

这就是 RAG 里常见的两阶段检索：

```text
第一阶段：ES BM25 取 top 100
    ↓
第二阶段：Cross-Encoder Reranker 对这 100 条逐条精排
    ↓
取 top 10
```

这种情况下：

- 第一阶段的 100 条，是 **BM25 已经排好序的 top 100**；
- 第二阶段的模型不是 BM25，而是 `bge-reranker` 这类 Cross-Encoder；
- 第二阶段会重新看 `query + chunk 正文`，判断语义相关性。

所以准确说法是：

```text
ES BM25 召回 top 100
    → Cross-Encoder 重排
    → top 10
```

而不是：

```text
ES 返回 100
    → BM25 再打一次分
    → top 10
```

因为 BM25 在第一阶段已经打过一次分了，再打一次基本是重复劳动。

##### 3. ES 里有没有“先粗排再精排”的机制？

有，叫 **rescore**，但和“再跑一遍 BM25”不是一回事。

ES 的 `rescore` 是：

```text
第一阶段：普通 query 取 top N（例如 100）
    ↓
第二阶段：只对这 100 条应用一个更贵的查询/打分函数
    ↓
重新排序，返回最终 top 10
```

例如：

```json
{
  "query": { "match": { "text": "基金费用" } },
  "size": 10,
  "rescore": {
    "window_size": 100,
    "query": {
      "rescore_query": {
        "match_phrase": { "text": "基金费用" }
      },
      "query_weight": 0.7,
      "rescore_query_weight": 0.3
    }
  }
}
```

这里的 `window_size: 100` 才是“先取前 100 再精排”的意思。
但第二阶段通常是一个更精确的查询（比如短语匹配、向量、外部模型），不是再跑一遍 BM25。

##### 4. 回到本项目

本项目不是“100 → 10”，而是：

```text
三路召回，每路 16 条
    ↓
RRF 融合，得到 26 条
    ↓
取前 12 条
    ↓
BGE-Reranker 精排
    ↓
最终 top 4
```

对应关系：

| 阶段 | 本项目 | ES 类比 |
| --- | --- | --- |
| 召回 | dense 16 + BM25 16 + metadata 16 | ES BM25 取 top 100 |
| 融合 | RRF → 26 条 | 无，通常是单路 |
| 精排 | BGE-Reranker 对 12 条重排 | Cross-Encoder 对 100 条重排 |
| 最终 | top 4 | top 10 |

所以本项目的思路和“ES 取 top 100 → rerank top 10”是一样的，只是：

- 候选数不是 100，而是每路 16；
- 多了一路向量和一路元数据；
- 多了 RRF 融合；
- 最终 top_k 是 4。

##### 5. 一句话回答

> **ES 不是“先返回 100 条再用 BM25 打分”。**
> 它是：query 分词 → 倒排索引找到所有命中的 chunk → 对这些 chunk 用 BM25 打分 → 按 `size` 返回前 N 条。
> 如果你说“先取 100 再取 10”，那通常是：**ES BM25 取 top 100 → Cross-Encoder 重排 → top 10**，第二阶段不是 BM25。

用一张图表示：

```text
用户：我要查询投资相关知识
        ↓
ES analyzer 分词
        ↓
倒排索引：找到包含查询词的 chunk 候选
        ↓
BM25 对候选打分（TF / IDF / 长度归一化）
        ↓
按分数排序，取 size=10 返回
        ↓
返回 chunk 原文 + metadata（_source）
```

两阶段版本：

```text
ES BM25 top 100
        ↓
Cross-Encoder 逐条精排
        ↓
top 10
```

本项目版本：

```text
dense 16 + BM25 16 + metadata 16
        ↓
RRF 融合 26 条
        ↓
Reranker 精排 12 条
        ↓
top 4
```

### 简化关系流向（通用理论）

```
【数据层】Wiki 原始文本
      ↓ 切片 → 双路：BGE-M3 输出 dense+sparse；BM25 由原文分词统计（不经模型）
【索引层】向量数据库（向量索引 + 稀疏向量索引，存 chunk ID + 原文 Payload）
          ＋（可选）BM25 倒排索引（Elasticsearch 等）
      ↓ dense 向量相似度检索（ANN）
【召回结果】对应 chunk ID 的 Wiki 文本片段
      ↓ 与 BM25 / 稀疏检索结果按 chunk ID 对齐去重 → RRF融合 → Rerank重排
【生成层】送入 LLM 生成最终答案
```

> 注：上图是**通用理论链路**，包含 dense + sparse + BM25 的组合。
> 本项目当前**没有使用 BGE-M3 的 sparse 输出**，实际是 **dense + BM25 + metadata 三路召回**。
> 两者可以对照理解，但不要把理论图中的“稀疏向量索引”误认为本项目已经实现的能力。

#### 本项目实际链路（与上图对照）

```text
【数据层】data/investment_wiki/*.md
      ↓ 按 ## 章节切分，再切成约 600 字 / 重叠 80 字的 chunk
【索引层】
      ├─ BGE-M3 向量（1024 维）→ Milvus 集合 investment_wiki（IVF_FLAT / L2）
      ├─ BM25Okapi（进程内，标题 + 章节 + 主题 + 正文，中文单字/双字分词）
      └─ MetadataIndex（title / chapter / topic / source 软打分）
      ↓ 三路各取 16 条（top_k=4 × candidate_multiplier=4）
【融合层】按 doc_id 去重 → 加权 RRF（0.55 / 0.30 / 0.15，rrf_k=60）
      ↓ 取融合结果前 12 条（top_k × 3）
【精排层】BGE-Reranker Cross-Encoder（当前已启用；模型缺失时降级 LexicalReranker）
      ↓
【生成层】取最终 top 4 → format_investment_context() 拼引用 → 投资回答模型
```
